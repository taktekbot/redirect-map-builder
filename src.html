Why each old address needs a redirect

When you move, rename or remove pages, each old address needs a permanent (301) redirect to the page that replaced it. Otherwise people and search engines arriving on the old link get a dead end. Writing a hundred of those rules by hand is slow, and the format is different on every host. Moving the whole site to a new domain? The redirects are one step of several; here is the full order.

Paste your old and new addresses below, one pair per line. Pick the tab for where your site lives (WordPress, Shopify, Squarespace, Wix, or your own server) and you get the list in the format it imports. Nothing is sent anywhere: the page reads your list and writes text.

Where to get the list of old addresses

Do this before you switch the old site off, while its pages still load.

  1. The old sitemap. Open /sitemap.xml on the old site (WordPress with Yoast or Rank Math uses /sitemap_index.xml, which links to the rest). Every address in it is a page Google was told about.
  2. Search Console. Under Indexing → Pages, open "Indexed" and export the list: these are the addresses people can still find in Google. The list stops at 1,000 rows (source), so for a bigger site, export Performance → Pages too and start with the pages that get clicks.
  3. Links you shared. Addresses in old newsletters, printed menus, QR codes and social profiles. These never show up in a sitemap, and they are often the ones people actually type.

Put the old addresses in one spreadsheet column, write the new page next to each, and paste both columns above. A page with no real replacement can be left out: it will return "page not found", which is the honest answer.

What it checks before writing anything

  • Chains. If /a goes to /b and /b goes to /c, both rules are rewritten to point straight at /c. Every extra hop is one more wait for the visitor, and Google's crawlers give up after 10 (source).
  • Loops. A page that redirects to itself, directly or through a chain, never loads. Those lines are dropped and listed.
  • Duplicates. The same old address twice with two different targets. The first one is kept; the rest are listed so you can decide.
  • Query strings. Rules like these match the path only, so /page?id=4 can't be told apart from /page. Cloudflare's bulk list refuses them outright. Those lines are skipped and listed.
  • Everything to the homepage. Google says sending many old addresses to one unrelated page, like the homepage, "might be treated as a soft 404 error" (source). If many lines point at /, you get a warning. Send each one to the closest real match, or let it return 404.

If your site is on WordPress, Shopify, Squarespace or Wix

You don't need a server file. Each of these keeps its own list of redirects, and the tab with its name gives you that list in the format it imports. The redirects live on the new site, so if you moved to one of these from somewhere else, connect your old domain to the new site first.

  • WordPress: install the free Redirection plugin, open its Import/Export page, and import the file, or paste the lines into "Import from text". Each line reads /old-url,/new-url,0,301; the 0 means "not a pattern" (source). WordPress has no redirect list of its own, which is why the plugin is needed.
  • Shopify: in your admin, go to Content → Menus → URL redirects → Import, and upload the file. Its columns are "Redirect from" and "Redirect to". One catch: Shopify only redirects an address that is broken. If a product or page still exists at the old address, the redirect does nothing until you delete it, or set the product to draft (source).
  • Squarespace: open Settings → Developer tools → URL mappings and paste the lines into the box, one per line, as /old-url -> /new-url 301. The box holds about 2,500 lines, and the first matching line wins, so put single pages above broad ones (source).
  • Wix: in your dashboard, go to SEO & GEO → Tools and settings → URL Redirect Manager → More Actions → Import redirects. The file has a header row, then the old path and the new address, at most 500 redirects per file (source). If Wix rejects the file, download its template from the same screen and paste the two columns under its headers.

Shopify and Wix send a 301 whatever you pick above. On the WordPress and Squarespace tabs, a 308 is written as 301, the permanent redirect both accept.

If you run your own server or host

  • Apache (.htaccess): at the top of the .htaccess file in your site's root folder. Uses RedirectMatch with anchored patterns, so /blog doesn't also catch /blog-archive the way a plain Redirect does (source).
  • nginx: inside the server { } block for your domain, then nginx -t and reload. Each rule is an exact match (location =). nginx checks regex locations in the order they appear and stops at the first match, so a ~ rule pasted below your site's own location ~ \.php$ would never catch /about.php. An exact match ends the search before any regex is tried (source). If the block already has a return outside any location, it runs first and these rules never fire; move it into location / { } (source).
  • Netlify and Cloudflare Pages (_redirects): a file named _redirects in the folder you publish. If the old page's file is still in that folder, Netlify serves the file and ignores the rule, unless the status ends in ! (source). Tick the box above if that's your case. Cloudflare Pages always applies its redirects, even when the old file is still there, and its format has no !, so leave the box unticked for it. It also stops at 2,000 redirects per file; past that, use Bulk Redirects (source).
  • Cloudflare Bulk Redirects (CSV): in the dashboard, create a Bulk Redirect List and upload the file. No header row; source without https://, target with it (source). The list does nothing until a Bulk Redirect Rule turns it on.
  • Vercel (vercel.json): merge the redirects array into your vercel.json. "permanent": true sends 308 and false sends 307, so for a 301 or 302 the tool writes statusCode instead (source).

GitHub Pages can't send real redirects. The nearest thing there is a page at the old address with an instant meta refresh, which Google reads as a permanent redirect (source).

After you deploy

Check a few old addresses from a terminal. You want one hop, a 301 or 308, and the right location:

curl -sI https://example.com/prices-2023 | grep -iE '^(HTTP|location)'
# HTTP/2 301
# location: https://example.com/prices

Then run the new address through the same command. It should answer 200, not another redirect. A Shopify store may print HTTP/2 103 first: that's Early Hints, a head start on loading files, not a redirect (RFC 8297).

On Windows, in PowerShell: curl.exe -sI https://example.com/prices-2023 | findstr /i /b "HTTP location"

No terminal? Paste an old address into a private browser window: the address bar should change to the new page, with no "page not found" on the way. Chrome hides https:// and www. there; right-click the address bar and tick "Always show full URLs" to see the whole address. A few days later, inspect the old address in Search Console's URL Inspection: "Page with redirect" means Google saw it.
